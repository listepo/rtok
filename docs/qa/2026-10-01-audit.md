### 1. `docs/config.md`: reference TOML fence swallows the semantic-cache section; heading skips h2 → h4

- **Severity:** high (fails every `pyrlyn/landing` Pages build, so no product site deploys)
- **Impact:** in any CommonMark renderer the "Reference file" code block (opened at line 67)
  does not end where it should. The `#### [plugins.proxy.semantic_cache]` heading, its table
  and its example (lines 337–363) render as code. The rest of the reference file
  (lines 365–417) renders as loose paragraphs. The `### [proxy.batch] / [proxy.flex] /
  [proxy.routing]` heading and `#### [proxy.batch]` (lines 422–445) end up inside a stray
  code block. The first heading after `## Reference file` is then `#### [proxy.flex]`
  (line 447). `pyrlyn/landing` CI (`check:seo`) fails on that: `heading skips a level: h2 → h4
  ("[proxy.flex]")`.
- **Environment:** `main` @ `966f067f`; markdown-it 14 (CommonMark), the same rules GitHub
  and the landing site use.
- **Steps to reproduce:**
  1. `awk '/^[ \t]*```/{print NR": "$0}' docs/config.md`. The fence opened at 67 is
     followed by ```` ```toml ```` at 354. That cannot close a fence, because a closing
     fence can't have an info string.
  2. Parse the file with markdown-it and list fences and headings.
- **Expected:** one `toml` fence for the reference file that ends before the prose. The
  semantic-cache section is a real `####` heading under a `###`, and no heading levels are
  skipped.
- **Actual:** markdown-it output:
  ```

  fence lines 67-364 info=toml

### 2. `rtok filter` drops all of stdin when it contains a non-UTF-8 byte

- **Severity:** high (silent data loss; this is the OpenCode `tool.execute.after` path)
- **Impact:** any tool output with one invalid UTF-8 byte disappears completely, and the
  exit status is still 0. That covers Latin-1 file content, binary in `git diff`/`cat`, and
  some compiler or locale output. The agent gets an empty tool result instead of the output,
  and nothing is archived, so `expand` can't recover it. This breaks the "lossless" rule in
  AGENTS.md. `rtok run` and `rtok filter --archive` decode lossily and keep the data, so only
  this path is affected.
- **Environment:** debug build at `a4753e08`, macOS arm64, fresh `HOME`.
- **Steps to reproduce:**
  1. `printf 'hello \xff world\nline2\n' | rtok filter | od -c`
  2. `printf 'a\xffb\n' | rtok filter --stdin; echo $?`
- **Expected:** the text passes through, filtered or with the bad byte replaced (U+FFFD), as
  `rtok run` and `filter --archive` already do.
- **Actual:** empty output, exit 0 (`od` prints nothing). `--archive` prints `a�b`.
- **Evidence:** `src/cli.rs:1487-1488` uses `let mut buf = String::new(); let _ =
  io::stdin().read_to_string(&mut buf);`. On invalid UTF-8, `read_to_string` returns
  `InvalidData` and leaves `buf` empty, and the error is discarded with `let _`. The
  no-plugin fallback at `src/cli.rs:1894-1896` has the same pattern.
- **Suggested fix:** read with `read_to_end` into a `Vec<u8>` and decode with
  `String::from_utf8_lossy` (as `--archive` does). Never discard the read error: on a real
  I/O error, echo what was read, or exit non-zero. Add a regression test that pipes
  `b"a\xffb\n"`.
- **Missing check / error handling:** `src/cli.rs:1488`, `src/cli.rs:1895`.

### 3. `rtok memory import` reports success for a missing or unreadable file

- **Severity:** medium
- **Impact:** a typo in the path, a directory, a permission error or a non-UTF-8 file all
  print `inserted 0  skipped 0  malformed 0` with exit 0. Scripts and agents think the import
  ran and the notes are lost without notice.
- **Environment:** debug build at `a4753e08`, macOS arm64, fresh `HOME`.
- **Steps to reproduce:**
  1. `rtok memory import /nonexistent.json; echo $?`
- **Expected:** `Error: /nonexistent.json: No such file or directory`, non-zero exit.
- **Actual:** `inserted 0  skipped 0  malformed 0`, exit 0.
- **Evidence:** `src/plugins/memory/import.rs:57` uses
  `std::fs::read_to_string(path).unwrap_or_default()`.
- **Suggested fix:** `std::fs::read_to_string(path).with_context(|| path.display().to_string())?`
  (the pattern `config/validate.rs:17` already uses). Test with a missing path.
- **Missing error handling:** `src/plugins/memory/import.rs:57`.

### 4. `rtok config validate` fails with ENOENT on a fresh install

- **Severity:** low
- **Impact:** the first command a new user is told to run (`rtok config validate`, in the
  reference file header) fails with a raw OS error. A second run passes: the failed run still
  leaves `config.toml` behind. Every other subcommand creates
  `~/.rtok/config.toml` from the reference first.
- **Environment:** debug build at `a4753e08`, macOS arm64, empty `HOME`.
- **Steps to reproduce:**
  1. `mkdir /tmp/h1 && HOME=/tmp/h1 rtok config validate; echo $?`
  2. Run the same command again.
- **Expected:** the default file is created (as `Config::load_with` does) and the output is
  `ok …/config.toml`. Or a clear message: "no config file yet; run `rtok config init`".
- **Actual:** step 1: `Error: /tmp/h1/.rtok/config.toml / Caused by: No such file or
  directory (os error 2)`, exit 1, and `config.toml` now exists. Step 2: `ok`, exit 0.
- **Evidence:** `src/cli.rs:972-974` calls `validate::issues(&path)`, which reads the file
  (`src/config/validate.rs:17`) without the `Config::ensure_user_file` call
  (`src/config/mod.rs:960`) that other subcommands get through `Config::load_with`.
- **Suggested fix:** call `Config::ensure_user_file(&home, config_file.as_deref())` when no
  explicit `path` is given, before `validate::issues`.
- **Missing check:** `src/cli.rs:973`.

### 5. `config validate` accepts out-of-range `semantic_cache.threshold` and any `embed_backend`

- **Severity:** medium (the feature is opt-in, but a false hit is a wrong answer)
- **Impact:** `plugins.proxy.semantic_cache.threshold` is a cosine-similarity floor, but
  `-1`, `0` or `5` pass `config set` and `config validate`. With `threshold <= 0`, every
  in-scope cached entry within the TTL matches, so the proxy serves an earlier, unrelated
  response. `embed_backend` takes any string. The docs say only `"hash"` (direct tier
  only) exists until P29, but a value such as `"openai"` or a typo turns on the semantic tier
  (`!= "hash"`) with the placeholder hash embedding. `plugins.read.delta_max_ratio = -3` is
  also accepted (it silently turns deltas off; a value above 1 sends diffs larger than the
  file).
- **Environment:** debug build at `a4753e08`, macOS arm64, fresh `HOME`.
- **Steps to reproduce:**
  1. `rtok config set -- plugins.proxy.semantic_cache.threshold -1`
  2. `rtok config set plugins.proxy.semantic_cache.embed_backend openai`
  3. `rtok config set -- plugins.read.delta_max_ratio -3`
  4. `rtok config validate`
- **Expected:** each `set` is rejected. `threshold` and `delta_max_ratio` must be in
  `(0, 1]`, and `embed_backend` must be in the supported set.
- **Actual:** every `set` succeeds and `validate` prints `ok`.
- **Evidence:** the range checks in `src/config/validate.rs:307-334` only cover integers,
  and the enum checks at `:336-360` don't list these keys. Use sites:
  `src/proxy/semantic_cache.rs:76,87,238` (`:81,92,278` on `fe5699e5`) and
  `src/plugins/read/cache.rs:39`.
- **Suggested fix:** add float range rules (`as_float()`) for
  `plugins.proxy.semantic_cache.threshold` and `plugins.read.delta_max_ratio`, plus an enum
  rule for `plugins.proxy.semantic_cache.embed_backend`. Add the matching negative cases to
  the validate tests.
- **Missing check:** `src/config/validate.rs:307-360`.

### 6. `config validate` accepts a malformed `stats.since`; `rtok stats` then fails

- **Severity:** low
- **Impact:** `stats.since = "7x"` passes validation. After that, `rtok stats` fails with
  `Error: bad --since unit in 7x`, which names a flag the user never passed. `rtok report`
  silently falls back to 30 days, and `doctor` silently skips the check (`doctor.rs:1040`
  `.ok()?`). The web/TUI model (`src/web/model.rs:384`) returns the error.
- **Environment:** debug build at `a4753e08`, macOS arm64.
- **Steps to reproduce:**
  1. `rtok config set stats.since 7x` (succeeds)
  2. `rtok config validate` prints `ok`
  3. `rtok stats` fails: `Error: bad --since unit in 7x`, exit 1
- **Expected:** step 1 or 2 rejects the value (`<n>`, `<n>d` or `<n>h`).
- **Actual:** as above: `set` exit 0, `validate` prints `ok …/config.toml` exit 0, `stats` exit 1.
- **Evidence:** `src/config/validate.rs` has no rule for `stats.since`. The only parser is
  `measure::stats::parse_since` (`src/measure/stats.rs:799,803`), whose messages hard-code
  `--since`. Callers handle its error three different ways: `rtok stats` propagates it,
  `src/doctor.rs:1040` drops it with `.ok()?`, `src/web/model.rs:384` returns it with `?`.
- **Suggested fix:** in `validate.rs`, run `measure::stats::parse_since` on `stats.since`. Have
  `parse_since` name its source (`stats.since` vs `--since`).
- **Missing check:** `src/config/validate.rs:336` (string rules); message at
  `src/measure/stats.rs:799,803`.

### 7. `RTOK_*` env overrides skip all value checks; `config validate` still says ok

- **Severity:** low
- **Impact:** the values `config validate` rejects in the file are taken as-is from the
  environment. One example is `RTOK_LOG_LEVEL=verbose`. `validate.rs` itself notes that an
  unknown level ranks most severe and silently drops everything below error
  (`crates/rtok-log/src/lib.rs:127-132`). `rtok config validate` prints `ok` in that state,
  so it can't explain why the logs went quiet.
- **Environment:** debug build at `a4753e08`, macOS arm64, fresh `HOME`.
- **Steps to reproduce:**
  1. `RTOK_LOG_LEVEL=verbose rtok config get log.level` prints `verbose`
  2. `RTOK_LOG_LEVEL=verbose rtok config validate` prints `ok …`, exit 0
- **Expected:** `validate` checks the merged config (file + project + env), or at least
  warns about env values it would reject in the file.
- **Actual:** step 1 prints `verbose`; step 2 prints `ok …/config.toml`, exit 0. The same
  value in `config.toml` is reported by `validate`.
- **Evidence:** `ConfigCmd::Validate` (`src/cli.rs:972-982`) runs `validate::issues` on the
  file path only; env values come in through `layers::load` (`src/config/layers.rs:500`),
  which deserializes them into `Config` with type checks and no value rules.
- **Suggested fix:** run the same per-key rules over the merged figment (`layers::load`) and
  report the source of each bad value (`config show --sources` already knows it).
- **Missing check:** `src/cli.rs:972-982` checks only the file; `src/config/layers.rs:500`
  loads env with type checks only.

### 8. `rtok run` / `rtok mcp -- …` report exit 1 for a child killed by a signal

- **Severity:** low
- **Impact:** a command killed by SIGKILL (OOM killer, timeout) or SIGTERM is reported as a
  plain failure (`1`), not `128+signal` (137/143). Agents and scripts can't tell "killed"
  from "failed", so OOM kills in test runs are hidden.
- **Environment:** debug build at `a4753e08`, macOS arm64, fresh `HOME`.
- **Steps to reproduce:**
  1. `rtok run -- sh -c 'kill -TERM $$'; echo $?`
  2. `rtok run -- sh -c 'kill -KILL $$'; echo $?`
  3. `sh -c 'kill -TERM $$'; echo $?` (reference)
- **Expected:** `143` and `137`, the same as the shell.
- **Actual:** steps 1 and 2 print `1`; step 3 prints `143`.
- **Evidence:** on Unix `ExitStatus::code()` is `None` for a signal death, and both call
  sites map `None` to `1` without looking at `ExitStatusExt::signal()`.
- **Suggested fix:** on Unix, map `ExitStatusExt::signal()` to `128 + sig` where the code is
  `None`.
- **Missing handling:** `src/plugins/cmd/run.rs:298` (`out.code.unwrap_or(1)`),
  `src/mcp/wrap.rs:90` (`code().unwrap_or(1)`).

### 9. `rtok graph index <path>` exits 0 for a path that does not exist

- **Severity:** low
- **Impact:** a typo prints `✅ indexed 0 files · 0 rows …` with exit 0, so a script or agent
  thinks the index was built.
- **Environment:** debug build at `a4753e08`, macOS arm64, fresh `HOME`.
- **Steps to reproduce:**
  1. `rtok graph index /nonexistent; echo $?`
- **Expected:** `Error: /nonexistent: No such file or directory`, non-zero exit.
- **Actual:** `indexed 0 files · 0 rows · 0 skipped · 0 read · exclude 0 · include 0 · mapped 0`,
  exit 0.
- **Evidence:** `src/cli.rs:1682` takes `path` as-is and passes it to `index::run_with`, whose
  walker yields nothing for a missing root. The sibling graph subcommands at `src/cli.rs:1703`,
  `src/cli.rs:1721` and `src/plugins/graph/status.rs:42` resolve `path` the same unchecked way
  (suspected same behaviour, not reproduced).
- **Suggested fix:** check `root.is_dir()` (or canonicalize with context) before
  `index::run_with`.
- **Missing check:** `src/cli.rs:1682` (also suspected `:1703`, `:1721`, `graph/status.rs:42`).
